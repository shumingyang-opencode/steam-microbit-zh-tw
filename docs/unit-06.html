6.1 什麼是事件驅動

傳統程式「從頭跑到尾」；事件驅動程式則「一直待命，事件發生時才執行對應程式碼」。

模式比喻範例
順序程式照食譜一步一步做顯示 → 等待 → 顯示
事件驅動客服電話，響鈴才接按 A 才執行、搖晃才執行
MakeCode 的事件積木：on button A pressed、on shake、on radio received、on logo pressed——都是「當…發生時」。

6.2 變數與狀態

  • 變數：記住數值（如計數器、狀態碼）。
  • 狀態：程式目前處於哪個「模式」。
範例
變數 count = 0
on button A pressed:
  count += 1
  show number count          ← 每按一次 +1

6.3 狀態機：讓行為有「模式」

狀態機用「狀態 + 轉換」組織行為：程式一次只處在一個狀態，事件讓它切換。

待機按A→顯示中按B→關閉按A→待機
範例
狀態 mode = "off"
on button A pressed:
  if mode == "off": mode = "on"; show icon 💡
  else:              mode = "off"; clear screen
on button B pressed:
  if mode == "on": show string "HELP"
為什麼要教狀態機：它是「程式邏輯」的核心思維，也連結數學的布林判斷與流程圖。

6.4 常見設計模式

  • 計數器：按一下 +1（練迴圈與變數）。
  • 切換開關：同一個按鈕開/關（狀態機最簡單應用）。
  • 多選單：按 A 換選項、按 B 確認。
陷阱：事件積木裡「只做很短的事」最好——太久會讓其他事件延遲。長時間任務放 forever。

6.5 Worked Example：三分鐘狀態機遊戲

範例
「心情切換器」
狀態：happy / sad / angry
on button A pressed:
  happy → sad → angry → happy（循環切換）
  依狀態顯示對應表情
on button B pressed:
  顯示目前狀態名稱（"I am HAPPY!"）

挑戰延伸：
  用「搖晃」隨機跳一個狀態 → 連結單元 10 的隨機數

動手：用狀態機做一個「三模式電筒」——關/暗/亮，按 A 循環切換。

6.6 練習：畫出事件與狀態的邊界

教案片段（35 分鐘）
情境：教室節能提醒器
狀態：NORMAL（正常）、WARNING（太吵或太暗）、SILENT（暫停提醒）
事件：讀值超過門檻、按 A 靜音、按 B 解除靜音
任務：
  1. 小組先畫三個狀態和所有箭頭，不寫程式
  2. 為每條箭頭寫「事件 + 動作」（例如按 A / 顯示 MUTE）
  3. 只實作兩條轉換，先用 LED 驗證，再補齊其餘轉換
  4. 同伴故意快速連按，記錄哪個狀態出錯
除錯問題可能原因修正策略
按一次跳兩個模式事件與 forever 同時改變 mode指定只有事件處理轉換
靜音後仍警報警報條件沒有檢查 mode條件加上 mode == WARNING
畫面殘留切換前未清除轉換時先 clear screen 再輸出

練習：把「心情切換器」增加 CALM 狀態，並寫出至少四條轉換；完成後用一句話解釋為何「狀態」比散落的 if 更容易測試。

  • 解釋事件驅動與傳統順序程式的差異。
  • 用事件積木設計互動行為。
  • 用狀態機讓行為有「模式」。

進階真實情境 Worked Example

以下是一個與上方不同的真實場景，展示多感測器 + 資料視覺化 + 跨裝置通訊的完整工作流。

進階 Worked Example
場景：「智慧教室控制系統」— 多狀態 + 多事件 + 多輸出
目標：教室的光、溫、音量同時影響 LED 顯示與蜂鳴器

狀態機設計：
  狀態：MONITOR（監測中）/ ALERT（警報）/ MUTE（靜音）/ SLEEP（休眠）
  事件：光暗、溫高、音量大、按A、按B、按A+B

程式骨架（MakeCode）：
  變數 mode = "MONITOR"
  forever:
    if mode == "MONITOR":
      light = light level
      temp = temperature
      if light < 40: mode = "ALERT"; 顯示 "暗"
      if temp > 32:  mode = "ALERT"; 顯示 "熱"
      顯示水銀柱
    if mode == "ALERT":
      閃爍 + 蜂鳴器
    if mode == "MUTE":
      不警報但持續量測
    if mode == "SLEEP":
      clear screen; pause 10s

  on button A pressed:
    if mode == "ALERT": mode = "MUTE"
    elif mode == "MUTE": mode = "MONITOR"
  on button B pressed:
    if mode != "SLEEP": mode = "SLEEP"
    else: mode = "MONITOR"

關鍵決策：
  → 為什麼狀態轉換放在事件而非 forever？
  → 因為 forever 每輪都會檢查，放在 forever 裡容易「重複觸發」
  → 事件只在按下的瞬間觸發一次，天然防抖（debounce）

深入原理擴充

MakeCode 事件模型的內部運作：MakeCode 的事件積木（on button A pressed 等）底層使用 JavaScript 的事件循環（Event Loop）。當硬體中斷觸發時，MakeCode runtime 將回呼函式（callback）放入事件佇列（queue），等主迴圈空閒時才執行。這解釋了為什麼事件積木裡不能放太久的操作——如果你在事件中放了 pause 5000ms，整個事件佇列會被阻塞，其他事件（如 button B）會被延遲。

陷阱案例：很多人以為「on button A pressed 裡的程式碼會立即執行」——事實上它會等到「下一個事件循環週期」才執行。如果你在 forever 迴圈中有一個很長的 pause（例如 5 秒），按鈕事件會被延遲最多 5 秒才響應。解決方案：在 forever 迴圈中使用短暫 pause（50-100ms），確保事件循環能及時處理使用者輸入。
症狀可能原因解決方案
按鈕反應延遲 1-2 秒forever 迴圈中的 pause 太長將 pause 縮短為 50-100ms；長任務拆成多段
同時按 A+B 只觸發一個事件MakeCode 的 A+B 事件需要同時按住改用 waspressed 檢測；或設計為「先按A再按B」的序列
狀態機跳過某個狀態事件與 forever 同時改變 mode統一在一個地方管理狀態轉換（建議在 forever 中判斷）
shake 事件太靈敏/不靈敏加速度閾值不適合當前使用情境用 acceleration (g) 的數值判斷，而非 on shake 事件
事件中斷 forever 迴圈後不會回來事件中的迴圈沒有退出條件事件中避免無限迴圈；改用變數旗標讓 forever 迴圈處理

進階挑戰題

  1. 非阻塞狀態機：用 MicroPython 實作同一個智慧教室控制系統。注意：MicroPython 沒有 MakeCode 的事件積木，你需要用 while True 輪詢 button_a.was_pressed()。比較兩種實作方式的「回應速度」與「程式碼複雜度」。
  2. 狀態機視覺化：為你的狀態機畫一張完整的「狀態轉換圖」（每個狀態是一個圓圈、每條箭頭標注「事件→動作」）。然後邀請同伴根據這張圖「走讀」你的程式碼，找出一個你沒注意到的邊界情況（edge case）。
  3. 防抖實作：設計一個「精確計數器」：按 A 加 1，但要避免「按一次加兩次」的問題。實作兩種方案：(1) 用 pause 延遲防抖 (2) 用變數旗標防抖。比較哪種更可靠。
