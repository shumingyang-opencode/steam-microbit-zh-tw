19.1 把整站串成一個學期

本單元把 20 個單元組織成一份18 週（一學期）課程藍圖：從認識板子到完成兩座大專案與成果展。

設計原則：「概念先教、技能接著練、然後做大專案、最後整合與展示」——讓每週都「接得上」。

19.3 器材與預算建議

項目建議量說明
Micro:bit v2每 2 人 1 台（或每人 1 台）核心器材
USB 線（資料線）與板數相當燒錄必備
電池盒每 2 台 1 個無線電/展示用
擴充板 + 元件包每組 1 包LED/蜂鳴器/伺服
手電筒等教具班級共用感測實驗
預算策略：先 2 人一組 + 角色輪替，是成本最低的起步；確認好用再加量。

進階真實情境 Worked Example

以下是一個與上方不同的真實場景，展示多感測器 + 資料視覺化 + 跨裝置通訊的完整工作流。

進階 Worked Example
場景：「18 週課程」的動態調整機制
目標：建立「核心穩定 + 彈性調整」的課程架構

核心骨架（不可動）：
  W1-2  基礎（認識板子 + 程式環境）
  W3-6  核心技能（LED/感測/事件/狀態機）
  W7-12 領域專案（S/T/E/A/M 各一）
  W13-16 大專案（環境感測站 + 遊戲）
  W17-18 評量 + 發表

彈性空間（可調整）：
  每週預留「+1 時段」（20 分鐘）：
  → 如果學生卡住 → 用來補救
  → 如果學生超前 → 用來加碼挑戰
  → 如果有外部活動（如校慶）→ 可併入或跳過

動態調整機制：
  每 3 週做一次「課程健康檢查」：
  1. 學生出口票分析（哪個概念最多人卡住？）
  2. 作品完成率（哪個里程碑延期？）
  3. 器材損壞率（需要補購嗎？）
  → 根據數據微調後 3 週的內容

迭代記錄表：
  W3 檢查：80% 學生能獨立完成 LED 動畫 → W4 正常推进
  W6 檢查：40% 學生狀態機卡住 → W7 加一節補救課
  W9 檢查：器材損壞 3 台 → 調整為 3 人一組
  W12 檢查：大專案進度落後 → 簡化 W13-14 的需求

深入原理擴充

課程迭代的科學：好的課程設計不是「完美的計畫」，而是「能適應變化的系統」。這與軟體開發的 Agile 方法論相通：

Agile 概念課程對應實踐方式
Sprint（衝刺）3 週一個小循環每 3 週做課程健康檢查
Retrospective（回顧）課程迭代根據學生表現微調後續內容
MVP（最小可行產品）核心骨架確保核心技能先教完
Backlog（待辦清單）彈性空間預留的 +1 時段可用
為何需要迭代：每個班級的起點、節奏、興趣都不同。「一份教案教到底」是不可能的——好的教師會根據「學生的回饋」不斷調整。這不是「沒有計畫」，而是「有計畫地適應」。
症狀可能原因解決方案
課程進度一直落後低估了學生需要的時間加入「+1 彈性時段」；簡化非核心活動
學生說「太簡單」缺少挑戰性任務準備「進階挑戰卡」；讓超前學生當小老師
器材損壞率太高管理 SOP 不夠嚴格加強器材管理訓練；準備備用板子
期末大專案做不完前期花太多時間、需求太廣前期用 MVP 標準；大專案需求分「必做」與「選做」
學生對專案主題沒興趣主題與學生生活脫節在 W1 做興趣調查；讓學生參與選主題

進階挑戰題

  1. 課程風險評估：為你的 18 週課程畫一張「風險矩陣」：列出 5 個最可能發生的問題（如：器材不足、學生程度落差大、時間不夠），並為每個問題準備「預防措施」和「緊急應變」。
  2. 動態調整案例：假設你在 W8 發現：60% 的學生還不會用「if 判斷」。你會如何調整 W9-12 的課程？請寫出具體的調整方案（哪些活動刪減、哪些活動替換、哪些活動保留）。
  3. 課程迭代記錄：如果你有實際教學經驗，回顧你的上一次課程，找出 3 個「如果重來我會改」的決定。用 Agile 的「回顧會議」格式寫出：做得好的 / 需改進的 / 下次嘗試的。
